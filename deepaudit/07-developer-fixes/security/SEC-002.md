# A. SEC-002 — Password-reset token can become reusable after a successful password change

## B. Severity

P1 — High and release blocking. A partial failure can leave the same reset link capable of changing the password again during its validity window.

## C. Confirmation status

**CONFIRMED BY SOURCE**

## E. Current implementation

The public reset handler leases a token, changes the Firebase password and revokes sessions, then finalizes DB consumption. Any error releases the lease. Release clears the lease, and an unreleased lease also becomes reusable after 60 seconds, while token expiry is 15 minutes.

## F. Reproduction evidence

Mock `updateUser` success and make session revocation or finalization fail. Catch calls release. A second lease succeeds immediately or after lease expiry, despite the first password side effect.

## G. Expected behavior

A reset capability is at-most-once. Once external identity mutation may have begun, the token can never return to reusable state; incomplete completion is reconciled.

## H. Root cause analysis

Reversible lease state wraps an irreversible external side effect, and catch unconditionally releases → successful password mutation can be followed by token reactivation.

## I. Detailed technical solution

- Model `ISSUED → APPLYING → CONSUMED` with APPLYING irrevocable to clients.
- Atomically transition to APPLYING before Firebase mutation using token hash/version.
- Never release after side-effect start; record completion/error metadata.
- Use outbox/reconciliation worker to finish revocation/audit and terminal state.
- Invalidate all outstanding custom tokens during rollout or temporarily use Firebase-native reset.

## J. Proposed patch / code-level repair

```diff
-const lease = await leasePasswordResetToken(token);
+const op = await beginPasswordResetOnce(token); // atomic ISSUED -> APPLYING
```
