## E. Current implementation

Resume photo/JSON fields persist verbatim and a live template renders photo as `<img src>`. Export launches Chromium with no sandbox and ignored TLS errors, then allows any HTTPS image/font/stylesheet. Authentication/entitlement narrows attackers but does not create a network boundary.

## F. Reproduction evidence

In a controlled fixture, store a resume photo URL to a loopback/private HTTPS server, publish/export, and observe the renderer request. This dynamic exploit was not run against any live system; the complete source chain is present.

## G. Expected behavior

Renderer fetches only controlled immutable assets. User URLs cannot reach loopback, private, link-local, metadata, DNS-rebinding or arbitrary internet targets; TLS validation and process isolation remain enabled.

## H. Root cause analysis

Untrusted persistent URL → direct template resource sink → broad HTTPS allow rule with DNS/redirect trust gaps → server-side browser network request. Disabled sandbox/TLS checks amplify impact.

## I. Detailed technical solution

- Ingest user images at upload time into controlled object storage after size/type/decode validation; store an asset ID, not remote URL.
- Allowlist exact asset origins in renderer; reject IP literals/private/reserved resolution, pin DNS result, and revalidate every redirect.
- Block all other requests and log redacted denials.
- Restore TLS verification; run Chromium in a sandboxed, nonprivileged container with egress deny-by-default, CPU/memory/time limits.
- Use existing network helper only as a component; connection pinning prevents DNS rebinding.

## J. Proposed patch / code-level repair

```diff
-if (url.protocol === 'https:' && ['image','font','stylesheet'].includes(type)) continueRequest();
+if (isApprovedImmutableAsset(request.url(), approvedOrigins, pinnedAddresses)) continueRequest();
+else abortAndAudit(request);
```
Template data resolves `photoAssetId` to a signed controlled URL generated server-side.
