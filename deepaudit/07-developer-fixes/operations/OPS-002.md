# A. OPS-002 — Cluster workers require the API module but never start its listener

## B. Severity

P1 — High. The checked-in multi-process path can fork healthy-looking workers that never listen.

## E. Current implementation

`cluster.js` forks workers whose code only `require('./index')`. `index.js` starts listening only inside `if (require.main === module)`, which is false when required by a worker.

## F. Reproduction evidence

Trace Node module semantics: under `cluster.js`, `require.main` is the cluster module, so the guarded startup block is skipped. No alternate worker call starts the server.

## G. Expected behavior

Direct and clustered modes call one idempotent startup function, await bootstrap, bind exactly once, report ready, and shut down cleanly.

## H. Root cause analysis

Listener side effect is guarded for direct execution while the cluster supervisor assumes `require()` performs it → workers initialize modules but do not bind HTTP.

## I. Detailed technical solution

- Extract an exported `startServer()` that owns bootstrap, listener creation, error handling and idempotency.
- Call it from the direct-entry guard and explicitly from cluster workers.
- Return the server/bootstrap handles for tests and graceful shutdown.
- Prevent double start with a promise/state guard.

## J. Proposed patch / code-level repair

```diff
+let startPromise;
+async function startServer() {
+  if (startPromise) return startPromise;
+  startPromise = bootstrapAndListen();
+  return startPromise;
+}
 if (require.main === module) {
```
