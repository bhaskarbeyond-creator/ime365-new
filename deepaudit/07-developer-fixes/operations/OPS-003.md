# A. OPS-003 — Stale build markers can falsely certify frontend/backend parity

## B. Severity

P1 — High. Release diagnostics can claim verified parity for artifacts from a different unavailable commit.

## C. Confirmation status

**CONFIRMED BY SOURCE**

## D. Affected code locations

- [`backend/COMMIT_SHA:1`](https://github.com/bhaskarbeyond-creator/ime365-new/blob/df5902dd897ff8e7955a738ac580f2a0d0263d0d/backend/COMMIT_SHA#L1)
- [`public_html/index.html:77`](https://github.com/bhaskarbeyond-creator/ime365-new/blob/df5902dd897ff8e7955a738ac580f2a0d0263d0d/public_html/index.html#L77)
- [`backend/routes/platform.js:73-88`](https://github.com/bhaskarbeyond-creator/ime365-new/blob/df5902dd897ff8e7955a738ac580f2a0d0263d0d/backend/routes/platform.js#L73-L88)

## E. Current implementation

HEAD is `df5902d…`, but both committed markers contain `24ada353…`. The platform route prefers Git when available and falls back to the stale file; packaged deployments without `.git` can report matching stale values as verified.

## F. Reproduction evidence

Compare `git rev-parse HEAD`, `backend/COMMIT_SHA`, and the HTML `build-sha` meta value. The two markers match each other but not HEAD.

## G. Expected behavior

CI generates one immutable release manifest from the exact source/artifact build and the API refuses to label mismatched or missing provenance as verified.

## H. Root cause analysis

Revision values are manually committed/fallback-based rather than atomically generated with artifacts → stale mutual agreement is mistaken for provenance.

## I. Detailed technical solution

- Generate a JSON release manifest during CI containing source SHA, frontend artifact digest, backend artifact digest, build time and pipeline ID.
- Embed the same signed/immutable manifest into frontend and backend packages.
- Never fall back from unavailable Git metadata to an unvalidated committed marker.
- Fail packaging/deploy if manifests differ or source is dirty.

## J. Proposed patch / code-level repair

```diff
- const sha = readGitSha() || readFile('COMMIT_SHA');
+ const manifest = verifyReleaseManifest(readBundledManifest());
+ if (!manifest.valid) throw new Error('Unverifiable release provenance');
```
CI writes the manifest after a clean build and verifies both packages before publishing.

## K. Step-by-step developer implementation

1. Define manifest schema and signing/digest rules.
1. Generate it in a clean CI checkout.
1. Embed it in both artifacts.

1. Add deploy-time parity gate and rollback manifest.

## M. Regression analysis

Local development needs an explicit `development/unverified` status rather than a false failure or fabricated SHA.

## O. Acceptance criteria

- One manifest is generated, never hand-edited.
- Frontend/backend digests and SHA match deployed artifacts.
- Missing/tampered provenance blocks release.
- Status distinguishes development-unverified from production-verified.

## P. Rollback plan

Redeploy the previous immutable artifact and its matching manifest.
