# A. API-001 — Payment webhook replay returns processed success without re-running processing

## B. Severity

P1 — High. Operators receive false success while financial/application state remains unreconciled.

## E. Current implementation

Two replay handlers select a stored webhook row, write an audit record, and return `REPLAY_PROCESSED`; neither calls provider-specific processing. Listing responses hard-code `signatureVerified:true`, but the baseline table stores no verification evidence or durable processing state.

## F. Reproduction evidence

Invoke either handler with a stored failed event in a disposable DB: source path performs SELECT/audit/response only. No order/subscription transition is called.

## G. Expected behavior

Replay uses the exact idempotent verified event processor, records attempts/outcome, and reports success only after a durable domain transition or verified idempotent no-op.

## H. Root cause analysis

Administrative replay was implemented as metadata acknowledgment rather than an invocation of the canonical webhook state machine; storage lacks verification/processing evidence.

## I. Detailed technical solution

- Create one provider-neutral `processStoredWebhook(eventId, replayContext)` service.
- Persist raw payload digest, provider event ID, signature verification result/time/key version, state, attempts, last error and domain idempotency key.
- Use one transaction/outbox boundary for state transitions.
- Have live ingestion and replay call the same processor; refuse replay for unverified or mutated payloads.
- Return 2xx processed only after durable success/idempotent completion.

## J. Proposed patch / code-level repair

```diff
- await auditReplay(event);
- return res.json({ status: 'REPLAY_PROCESSED' });
+ const result = await webhookProcessor.processStored(event.id, {
+   actorUid: req.user.uid,
+   reason: req.body.reason,
+ });
+ return res.status(result.completed ? 200 : 409).json(result.publicView);
```
