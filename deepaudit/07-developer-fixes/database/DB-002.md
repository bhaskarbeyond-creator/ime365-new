# A. DB-002 — Failed baseline migration can return a pooled session with foreign-key checks disabled

## B. Severity

P1 — High. Subsequent writes on the same pooled connection could bypass referential integrity.

## E. Current implementation

The baseline sets `FOREIGN_KEY_CHECKS=0` and restores it only at its final statement. The runner stops at a failing statement and releases the connection in `finally` without restoring/verifying the session variable.

## F. Reproduction evidence

Inject a failing baseline statement after line 6. Control jumps out before line 1005; the runner releases the session at line 222.

## G. Expected behavior

Every pooled connection returns with validated session invariants. If restoration cannot be proved, the connection is destroyed, not pooled.

## H. Root cause analysis

Session-scoped migration mutation + early statement failure + unconditional pool release → contaminated connection reuse.

## I. Detailed technical solution

- Track all session variables changed by migration execution.
- In `finally`, issue `SET FOREIGN_KEY_CHECKS=1`, read it back, then release.
- If restore/readback fails, destroy/end the connection so it cannot reenter the pool.
- Prefer a dedicated nonpooled migration connection and transaction-safe migration design where supported.

## J. Proposed patch / code-level repair

```diff
 } finally {
-  connection.release();
+  try {
+    await connection.query('SET FOREIGN_KEY_CHECKS = 1');
+    const [[row]] = await connection.query('SELECT @@FOREIGN_KEY_CHECKS AS enabled');
+    if (Number(row.enabled) !== 1) throw new Error('FK checks not restored');
+    connection.release();
+  } catch (restoreError) {
+    connection.destroy();
+    throw restoreError;
+  }
 }
```
