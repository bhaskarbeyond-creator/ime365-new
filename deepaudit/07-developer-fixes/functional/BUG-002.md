## E. Current implementation

After AI returns text, the component enqueues `setState({letterBody: generated})` and immediately awaits `handleSaveCoverLetter()`. The save handler reads `this.state.letterBody`, can submit the old body, and on success writes that old body back. Save has no complete catch/finally, so rejection can strand `isSaving` and gives no durable error/retry contract.

## F. Reproduction evidence

Start with body A and mock AI response B. Because class `setState` is asynchronous, the immediately called handler can snapshot A. Today BUG-001 causes save to fail before HTTP; repair of BUG-001 exposes stale persistence.

## G. Expected behavior

The exact generated/accepted text is passed explicitly to persistence, only the latest non-aborted generation saves once, and all error paths preserve text and reset UI state.

## H. Root cause analysis

State update scheduling was used as an inter-function data transport → save observes prior render state; missing terminal error handling magnifies failure.

## I. Detailed technical solution

- Change save to accept an explicit body/payload override and never depend on a just-enqueued state update.
- Use the `setState` callback or construct one immutable payload from the AI response.
- Track request/generation ID; ignore aborted/out-of-order responses.
- Wrap persistence in try/catch/finally, retain unsaved generated text and expose retry.
- Add dirty/autosave semantics per UIUX-004.

## J. Proposed patch / code-level repair

```js
const generated = response.coverLetter;
this.setState({ letterBody: generated, step: 2 });
await this.handleSaveCoverLetter({ letterBody: generated, generationId });

handleSaveCoverLetter = async (override = {}) => {
  this.setState({ isSaving: true });
  try { return await save({ ...this.state, ...override }); }
  catch (error) { this.setState({ saveError: toUserMessage(error) }); throw error; }
  finally { this.setState({ isSaving: false }); }
};
```
